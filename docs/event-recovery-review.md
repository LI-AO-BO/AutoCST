# CST 完成事件与异常恢复审查

日期：2026-10-08。本文记录方案审查和已读取的官方/本机证据，不表示事件版执行器已经通过真实仿真验收。本次只写本文档，未修改执行器、后端、数据库或 CST 工程。

这是实现前的历史方案审查，后续实机验收见 [v0.2 验证记录](../VERIFICATION_v0.2.md)。本页引用的官方安装资料与本地探针日志不随公开仓库分发。

## 结论与证据

正常执行可使用独立工作进程调用官方 `Model3D.run_solver()`，执行器等待该进程的 Windows 完成信号。完成后核验工作进程原子收据和 CST 成功状态，再保存、导出、分析；无需每隔若干秒向 CST 查询是否结束。

本机 CST 2025.2 官方帮助 `C:\Program Files (x86)\CST Studio Suite 2025\Online Help\Python\source\cst.interface.html` 第 401–403 行说明：`run_solver()` 等待求解和后处理结束，错误时抛异常。第 407–409 行的 `start_solver()` 则异步返回。此次查阅该接口页未找到可订阅的通用求解完成回调；不能把检索未发现写成整个 CST 套件绝无此功能。

本机真实日志证据：`.autocst/backend_probe/metasurface_canonical_20261008T141214/project/Result/Model.log` 第 644、672、675、678 行依次记录求解计算结束、开始后处理、后处理完成、创建参数化 1D 结果。另一个真实日志 `metasurface_v02_20261008T135923/project/Result/Model.log` 第 4508–4541 行显示，计算结束与后处理完成相差约 2 秒。**日志中的计算成功句子早于后处理与结果创建，不能作为最终完成判据。**这些日志来自本机频域算例，未验证为跨求解器、版本和语言环境的稳定协议。

Windows `WaitForMultipleObjects` 可同时等待进程、事件与计时器句柄；需要 `SYNCHRONIZE` 权限，等待期间关闭其中句柄会导致未定义行为。Windows 8 及更新版本的相对等待超时不计算低功耗时间，因此预算应同时以持久时间记录核对。[Microsoft：WaitForMultipleObjects](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitformultipleobjects)

## 正常路径的最小契约

1. 在调用 `run_solver()` 前持久写入唯一启动意图，包含 `run_id`、`binding_id`、工作进程 PID/创建时间、CST PID/创建时间、工程路径、输入哈希、执行版本和启动时间。工作进程自身在调用前落盘身份，避免父进程写收据前退出留下无法识别的工作进程。
2. 后台执行器等待工作进程句柄、控制事件、CST 主进程句柄和预算截止事件。健康心跳只更新执行器状态；不因心跳超时而查询 CST。控制暂停只阻止下一轮，取消当前求解另走明确的停止操作。
3. 工作进程在 `run_solver()` 返回后读取成功信息，先原子写完成收据，再正常退出。收据包含绑定身份、结果状态、结束时间与异常信息。**进程退出只是检查收据的触发条件，退出码 0 也不能单独代表科研结果有效。**
4. 只有收据与绑定匹配、CST 当前运行成功、保存和指定结果导出成功，才能进入分析。失败、取消、连接丢失、无收据退出分别保留；没有成功收据时不得重复 `run_solver()`。
5. 等待器不能在健康心跳路径中清理或结束工作进程；停止超时只表明本工具与 CST 的交互未确认，不能据此声称 CST 已停止。

## 重启后如何继续等待原任务

| 恢复时观察 | 处理 | 禁止推断 |
| --- | --- | --- |
| 原工作进程存活，PID 与创建时间匹配 | 重新取得可等待进程句柄，继续等待退出信号；不启动新工作进程求解 | PID 相同本身不能证明是原进程 |
| 原工作进程已结束，匹配的完成收据存在 | 幂等恢复保存/导出/分析阶段 | 不把重做后处理变成重新求解 |
| 原工作进程已结束或不可识别，原 CST 仍活且工程匹配 | 注册工程结果目录变更通知，然后进行一次有界状态核查；仍在运行则等待文件变化、控制或截止事件 | 不再次调用 `run_solver()` 来“接上等待” |
| CST 已退出，但已保存工程与成功收据完整 | 按已保存哈希离线恢复结果导出 | 不打开工程重新求解以补证据 |
| 身份不匹配、状态无法确认、证据不完整 | `needs_attention` 并保留占用；等待明确恢复/取消 | 不默认为失败后释放并启动另一份求解 |

目录通知方案可采用 `ReadDirectoryChangesW` 的异步模式：以 `FILE_LIST_DIRECTORY` 权限打开目录，设置 `FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OVERLAPPED`，使用独立 `OVERLAPPED.hEvent`；关注文件名、大小和最后写入变化。缓冲区溢出会丢弃细节，必须重新枚举并核查；通知可能受缓存刷新延迟影响。[Microsoft：ReadDirectoryChangesW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw)

具体恢复规则：

- 优先监听该工程 `<project>/Result/` 下的 `Model.log` 与已验证相关结果变化；不要递归监听整个 run 目录，否则本工具写 `api_calls`、分析或状态会触发自身，形成无限核查。
- **先注册通知，再读取当前状态。**完成可能早于监听建立，因此注册后必须立即核查一次；收到变化后重新布置监听，再执行有界核查，避免核查期间错过结束写入。
- 多个变化可合并成一次状态核查；变更、重命名、重建、缓冲区溢出均表示“需要重新读取”，不表示成功。记录触发原因与核查证据，不能把每条日志写入计为一个完成事件。
- 核查仍在运行时回到事件等待；核查已停止时仍要求 `SUCCESS`、本 run 的启动/清理记录、完整的目标结果和保存/导出验证。仅日志关键字、文件存在、文件大小稳定、CST 主进程仍存在均不足以完成任务。
- 如果同步工作进程已丢失，就失去了官方同步调用返回这一强证据。恢复时的成功状态、结果完整性和后处理就绪检查应以本机真实故障注入验收；无法确认时保持 `needs_attention`，不要声称通用求解器恢复已保证。
- 目录不存在时监听最近的已存在工程目录以等待 `Result` 创建；出现后迁移到结果目录。CST 主进程退出与预算截止也应作为等待事件，避免没有文件变化时永久等待。
- 关闭异步监听前取消相应 I/O 并等待其完成，再释放缓冲区、`OVERLAPPED` 和句柄。`CancelIoEx` 返回只确认取消请求已发出，不等于 I/O 已经结束。[Microsoft：CancelIoEx](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex)

以上是基于官方 Windows 通知接口和本机日志路径的可实施方案；本轮没有创建监听器或开展重启中的真实求解验证，也没有发现可直接信任的 CST 通用完成文件。

## 提交与控制事件的可靠性

建议单一后台消费者使用当前用户会话内命名 auto-reset Event。SQLite 队列和控制请求是事实来源，Event 只表示“请读一次待办”；多个提交合并为一个信号时，消费者仍应读完所有待办。auto-reset Event 在无人等待时可维持信号；命名对象最后一个句柄关闭后销毁，不具备跨重启持久性。[Microsoft：Event Objects](https://learn.microsoft.com/en-us/windows/win32/sync/event-objects)、[Microsoft：CreateEventW](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createeventw)

顺序固定为：执行器先创建/打开 Event，再初次核对数据库；提交端先提交数据库事务，再 `SetEvent`。发送信号失败应返回“任务已保存但唤醒未确认”，重试沿用幂等键。提交端在事务提交后、发信号前崩溃仍存在空隙：可由下一次控制/提交事件、执行器启动核对或健康恢复时只检查数据库待办来补偿；这些动作不查询 CST。若完全禁止健康恢复读取待办，必须接受这一崩溃场景需要明确唤醒，不能宣称绝不丢即时通知。

命名包含规范化 workspace 哈希与用户/会话隔离，所有消费者使用相同名称规则；不以保存 PID 代替句柄身份。使用 manual-reset Event 时，复位和再次读取数据库的顺序需单独验证，避免清除并发提交的新信号。

## 必要验收

- 正常小算例：从启动到官方同步返回之间，CST 状态查询次数为 0；返回后立即保存/分析，完成延迟不与某个轮询间隔绑定。
- 同步工作进程正常返回、抛异常、异常退出且没有收据，分别得到成功后处理、失败记录和待核查状态。
- 执行器在工作进程仍存活时重启：重新等待同一进程，启动意图与求解次数仍为 1。
- 工作进程在 CST 仍计算时被故障注入终止：通过目录变化触发核查；从头到尾不发送第二次求解命令。
- 完成发生于监听建立之前或核查期间、日志重命名、通知缓冲区溢出、工作进程 PID 复用，均不漏掉既有证据或误归属结果。
- 求解计算完成但后处理仍进行时不能进入最终成功；CST 主进程退出、无文件变化、预算到期和取消未确认均可结束等待并给出明确状态。
- 并发提交/控制、消费者尚未等待时发信号、发送方提交后崩溃：请求仍在数据库，信号合并不会丢任务或重复执行。
- 心跳持续、控制可响应，与“十几小时真实 CST 求解完成”“Codex 应用关闭后恢复”“对话即时唤醒”分别留证，不能用其中一项替代其他验收。
